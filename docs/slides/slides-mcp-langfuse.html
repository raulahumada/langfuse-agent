El problema

Cada app integraba cada herramienta a mano

Con N aplicaciones y M herramientas hacen falta N×M conectores. Con un protocolo común, cada lado se implementa una sola vez.

Definición

Model Context Protocol (MCP)

Un estándar abierto para que las aplicaciones de IA se conecten con sistemas externos: datos, herramientas y flujos de trabajo.

La analogía

USB-C para la IA

Un solo conector en vez de un cable distinto por cada dispositivo.

Qué estandariza

El lenguaje, no la lógica

Cómo descubrir y llamar capacidades. Qué hacen es cosa de cada servidor.

Sobre qué se apoya

JSON-RPC 2.0

Mensajes JSON de pedido y respuesta, sobre stdio o HTTP.

El modelo no "sabe" de GitHub ni de Langfuse. Solo ve una lista de herramientas con descripción y schema, y decide cuál llamar.

Qué ofrece un servidor

Tools, Resources y Prompts

Tools

Funciones que el modelo invoca

Con nombre, descripción y JSON Schema de argumentos. Pueden tener efectos.

Es lo que más se usa. Todo este proyecto trabaja con tools.

Resources

Datos que se leen

Contenido identificado por URI: archivos, registros, páginas. Solo lectura.

Los elige la aplicación, no el modelo.

Prompts

Plantillas reutilizables

Instrucciones parametrizadas que el usuario dispara, como un comando.

Útiles para flujos repetidos.

Del lado del cliente hay capacidades que el servidor puede pedir: roots (qué carpetas puede ver), sampling (pedirle una respuesta al modelo) y elicitation (preguntarle algo al usuario).

Tools

Lectura, escritura o ambas

Solo lectura

Consultan, no cambian nada

Leer un archivo, listar commits, pedir métricas. Se pueden repetir sin riesgo.

Marcadas con readOnlyHint: true.

Escritura

Cambian el estado

Crear una rama, abrir un PR, enviar un mensaje. Pueden ser irreversibles.

Piden más cuidado y, a veces, aprobación.

Ambas

Mezcla o depende de los argumentos

Un servidor con tools de los dos tipos, o una tool que según el parámetro lee o escribe.

Conviene separar y etiquetar cada una.

AnotaciónSignifica
readOnlyHintLa tool no modifica su entorno
destructiveHintPuede hacer cambios destructivos, no solo agregar
idempotentHintLlamarla de nuevo con los mismos argumentos no cambia nada más
openWorldHintInteractúa con un mundo abierto (internet, terceros) o solo con algo cerrado
Son pistas para el cliente, no garantías: el control real está en el código y en los permisos.

Balance

Ventajas y desventajas

Ventajas

  • Se escribe una vez, sirve para cualquier cliente compatible.
  • Descubrible: el agente aprende las tools en ejecución.
  • Desacopla el agente del sistema: cambiás uno sin tocar el otro.
  • Ecosistema grande y abierto, con SDKs en varios lenguajes.
  • Un lugar claro para poner límites y permisos.

Desventajas

  • Cada tool ocupa contexto: muchas tools = más costo y más confusión.
  • Superficie de ataque: prompt injection y servidores no confiables.
  • Otra pieza para desplegar, versionar y monitorear.
  • Calidad desigual entre servidores de la comunidad.
  • Un estándar joven: la spec sigue cambiando.

Antes de construir

Qué es Langfuse y para qué sirve

Una plataforma open source de observabilidad para aplicaciones con IA: guarda lo que hizo tu app, paso a paso, para que puedas entenderlo, medirlo y mejorarlo.

El problema

Una app es una caja negra

Si algo falla o se vuelve lento, no sabés qué paso pasó, con qué datos ni cuánto costó.

Qué hace

Registra cada paso

Tu código manda trazas: qué se ejecutó, cuánto tardó, qué entró y salió, y si hubo error.

Para qué

Ver, medir, mejorar

Errores, latencia, costo y tokens en un panel; evaluar la calidad de las respuestas.

Es el “Datadog de las apps con IA”: en vez de adivinar, mirás lo que realmente pasó.
En el proyecto Langfuse es la fuente de datos: el agente la lee a través de nuestro MCP.

Crear una tool

Una función tipada es una tool

mcp_langfuse/server.py
python
mcp = FastMCP("langfuse-ops", instructions=INSTRUCTIONS)

@mcp.tool(annotations={"readOnlyHint": True})
async def list_logs(
    level: Literal["DEBUG", "DEFAULT", "WARNING", "ERROR"] | None = None,
    since_minutes: Annotated[int, Field(ge=1, le=20160)] = 60,
    limit: Annotated[int, Field(ge=1, le=100)] = 25,
) -> dict[str, Any]:
    """Lista observaciones recientes; usá level=ERROR para ver fallos."""
    try:
        return await lf().observations(level=level, since_minutes=since_minutes, limit=limit)
    except LangfuseError as exc:
        return {"error": str(exc)}
  • El nombre sale de la función, la descripción del docstring, el schema de los type hints.
  • Literal y Field validan antes de ejecutar: un nivel inválido se rechaza.

Diseñar para el modelo

De logs crudos a un diagnóstico

Antes · observaciones crudas

  • El mismo fallo repetido en cada span padre e hijo.
  • Sin tipo de excepción ni archivo.
  • Mensajes con valores variables: nada se agrupa.
  • Resultado: respuestas pobres del agente.

Después · diagnose_errors

  • Colapsa por trace: una falla cuenta una vez.
  • Agrupa por código de error, no por mensaje.
  • Agrega ubicación, contexto, stacktrace y ejemplos.
  • Ordena por impacto.

Dónde

Remoto y oficial

Qué se publica

Dos toolsets

X-MCP-Toolsets: repos,pull_requests deja ~16 tools en vez de decenas.

Qué se usó

Leer y proponer

get_file_contents, create_branch, create_or_update_file, create_pull_request.

Token fine-grained de un solo repo: Contents: write, Pull requests: write, Metadata: read. Con solo lectura, GitHub responde 403 y el agente solo puede sugerir.
Aprendido Ni un MCP bien armado funciona si el token no tiene los permisos.

def apply_discount(subtotal, coupon):

        return subtotal

Diseño de tools

Pensá en el modelo, no en la API

01

Pocas y con propósito

Cada tool ocupa contexto. Mejor 6 buenas que 60.

02

Devolvé conclusiones

Agrupá, ordená y recortá. No vuelques JSON crudo de 10.000 líneas.

03

Descripción como prompt

El docstring le dice al modelo cuándo usarla. Escribilo para él.

04

Argumentos acotados

Literal, rangos y defaults: menos margen para equivocarse.

05

Errores como datos

Devolvé {"error": ...} legible, no un traceback.

06

Nombres claros

diagnose_errors se entiende solo; query2 no.

Autenticación

Cómo se autentica un MCP

TransporteCómo se autenticaDetalle
stdio (local)Credenciales del entornoEl cliente lanza el proceso y le pasa variables de entorno. La spec indica no usar su flujo de autorización y leer las credenciales del entorno.
HTTP (remoto)OAuth 2.1 (estándar de la spec)El servidor actúa como resource server y el cliente como cliente OAuth: el usuario autoriza y el cliente recibe un token de acceso.
HTTP (simple)Token o API key en cabeceraAuthorization: Bearer .... Es lo más común en la práctica: tokens personales o de servicio.
  • El servidor es quien valida: cada pedido HTTP lleva el token y se verifica su alcance.
  • El token debe ser de mínimo privilegio y revocable; nunca va en el código ni en los logs.
Autenticación = quién sos. Qué podés hacer lo define la autorización: los permisos del token.

Lo que se llevan

Teoría

MCP es un estándar abierto

Un protocolo para publicar y descubrir herramientas. Se escribe una vez y sirve a muchos clientes.

Práctica

Un servidor es una capa fina

Funciones tipadas, validación, lógica en módulos aparte y tests sin el protocolo.

Criterio

Diseñá para el modelo

Pocas tools, resultados con conclusiones, errores legibles y límites reales.

Un agente es tan útil como las herramientas que le das y tan seguro como los límites que le ponés.
